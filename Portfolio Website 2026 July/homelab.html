Tier 1 · Physical Infrastructure

Compute & Storage

The bare-metal foundation everything else runs on.

🖥 Hypervisor

Proxmox VE

Xeon E5-2660 v2 10C / 20T 128 GB ECC GTX 1050 Passthrough
  • →Runs all VMs & containers on bare metal
  • →Network isolation enforced at virtual bridge level
  • →Snapshot & backup management built in
  • →GPU passed directly to VM for compute workloads
ECC RAM is critical for a hypervisor. A single bit-flip in regular RAM can silently corrupt every VM on the system. ECC detects and corrects single-bit errors in real time — standard in every production server.

The 20-thread Xeon allows genuine parallelism: OPNsense, TrueNAS, Windows Server, and multiple Docker containers all run simultaneously without competing for CPU time.
💾 Storage

TrueNAS Core

4+ TB ZFS Pool NFS Share SMB Share SMART Monitoring
  • →Stores all VM snapshots & backups
  • →NFS for Proxmox; SMB for Windows VMs
  • →ZFS checksums every block — detects corruption
  • →Scheduled scrubs catch drive degradation early
Standard RAID can return silently corrupted data with no error — called "bit rot." ZFS checksums every block and verifies it on every read. In a backup system, data integrity isn't optional.

NFS vs SMB: NFS is low-overhead for large sequential writes (VM backups). SMB is used for Windows clients — it's the native protocol with zero compatibility friction.
🎮 Endpoints

Client Nodes

Ryzen 7 7800X3D RTX 3060 Ti GTX 1060 (Plex) PlayStation 5
  • →Isolated on VLAN 20 — can't reach admin layer
  • →GTX 1060 does Plex GPU transcoding
  • →All streaming routed through Surfshark VPN
  • →Used for VLAN & firewall rule testing
Consumer devices run unverified firmware and connect to external networks constantly — high-risk. Placing them on VLAN 20 means even a fully compromised console cannot reach the hypervisor or storage. The firewall enforces this at the packet level.

GPU transcoding in Plex drops CPU load from ~400% to under 10% per 4K stream. Without it, simultaneous streams would saturate the server.

Tier 2 · Network & Security

Zero-Trust Perimeter

Every device lives in a segment. Every segment has a deny-by-default policy. Nothing communicates unless explicitly allowed.

Why segment the network at all?

In a flat network, every device can freely talk to every other device. A compromised IoT bulb could send traffic to the NAS. A guest device could reach the Proxmox management UI. VLANs create hard logical boundaries — combined with OPNsense firewall rules, even a fully compromised device in one VLAN hits a wall trying to reach another. This is the same model used in enterprise and cloud environments.

VLAN Segments

VLAN 10

Administration

Proxmox · TrueNAS · OPNsense Management

  • →No inbound connections from any other VLAN
  • →Reachable only via WireGuard VPN remotely
  • →All management traffic stays local
Proxmox and TrueNAS both expose web UIs. If reachable from untrusted devices, a single compromised endpoint could give an attacker full control over every VM and all stored data. The admin VLAN means you need physical access or a verified VPN connection to manage infrastructure.
VLAN 20

Gaming & Clients

Gaming PCs · PlayStation 5 · Streaming

  • →Internet access allowed
  • →No access to VLAN 10, 30, or 40
  • →QoS bandwidth priority for low-latency gaming
Gaming hardware runs unverified firmware and is constantly connected to external servers. Even if a console were exploited, it physically cannot reach the hypervisor or NAS. The firewall drops those packets before they ever arrive.
VLAN 30

IoT & General

Smart Home Devices · Untrusted Guests

  • →Outbound HTTPS only (port 443)
  • →Zero inter-VLAN routing — most restricted
  • →Pi-hole blocks IoT tracking & botnet domains
IoT devices are notorious security risks — outdated firmware, no patch cycle, weak auth. They can reach their cloud servers. They cannot talk to anything else on the network. Industry best practice.
VLAN 40

VPN Tunnel

Remote Laptop · Mobile Devices (WireGuard)

  • →Auth by public-key cryptography — no passwords
  • →VLAN 40 → VLAN 10 allowed; 20/30 denied
  • →Encrypted in transit — safe on public WiFi
VPN connections land in VLAN 40, not directly in VLAN 10. Even with a stolen VPN credential, firewall rules still restrict access. A compromised key can't pivot to client or IoT segments.

Security Services

🔥 OPNsense Firewall

VM on Proxmox · FreeBSD-based

  • →Stateful packet inspection on all traffic
  • →Default-deny on every VLAN interface
  • →NAT, port forwarding, QoS traffic shaping
  • →Transparent DNS redirect to Pi-hole
Running OPNsense as a VM means its config is snapshotted — a broken rule rolls back in seconds. It provides enterprise features (IDS/IPS, traffic inspection, cert management) that no consumer router offers.

🔐 WireGuard VPN

LXC Container · UDP 51820

  • →Public-key auth — no passwords to brute force
  • →Split tunneling: only internal traffic routed
  • →Unique key per device — individual revocation
  • →~4,000 lines vs OpenVPN's ~100,000+
WireGuard's minimal codebase is far easier to audit for vulnerabilities. Modern cryptography (ChaCha20, Curve25519) and UDP transport deliver 3–5× faster connections than OpenVPN with lower latency — important for remote management.

🕳 Pi-hole DNS Filter

LXC Container · Network-wide DNS

  • →Blocks ads, trackers, malware C2 domains
  • →Applied to every device via DHCP
  • →OPNsense intercepts DNS bypass attempts
  • →Query log gives full network visibility
Malware must resolve a domain before it can connect. Blocking at DNS prevents the connection before it's ever established — works on every device including consoles and IoT. OPNsense redirects any device trying to bypass Pi-hole back to it.

Firewall Rule Logic

opnsense_fw_rules.txt
# Default policy on ALL VLAN interfaces: DENY ALL # Rules below are explicit ALLOW exceptions only VLAN 10 (Admin) → Any : ALLOW # Admin can reach everything VLAN 20 (Clients) → WAN : ALLOW # Clients get internet VLAN 20 (Clients) → VLAN 10/30/40 : DENY # Clients cannot touch infrastructure VLAN 30 (IoT) → WAN port 443 : ALLOW # IoT: HTTPS only VLAN 30 (IoT) → Any VLAN : DENY # IoT fully isolated VLAN 40 (VPN) → VLAN 10 : ALLOW # VPN peers manage infrastructure VLAN 40 (VPN) → VLAN 20/30 : DENY # VPN scope limited to admin only # Transparent DNS enforcement (prevents Pi-hole bypass) Any VLAN → UDP/TCP 53 : REDIRECT → Pi-hole @ 10.0.10.5

Full Virtual Machines

  • →DNS & DHCP roles for the domain
Active Directory is the backbone of virtually every enterprise Windows environment. No study guide replaces hands-on AD — user/group management, OU design, and GPO troubleshooting have to be practised live. This directly mirrors day-one work in a corporate sysadmin role.

🐧 Ubuntu Server VM

Linux Sandbox

  • →Bash scripting & automation practice
  • →Package testing before production deploy
  • →Domain-joined for Linux-AD integration tests
Changes tested here can't break production services. If something goes wrong, the VM rolls back to a snapshot in seconds. This mirrors the "dev → staging → prod" pipeline used in real infrastructure teams.

💻 Windows 10 Client VM

Client Simulation

  • →Domain-joined end-user workstation
  • →Verifies GPO application from user perspective
  • →Tests firewall rules from a real client
A domain controller without a client to verify against is untested infrastructure. This VM simulates a real end-user workstation — confirming GPOs apply correctly and network rules behave as expected from the user's point of view.

B. Self-Hosted Services

Docker on Alpine LXC

All services run in Docker containers inside a single lightweight Alpine LXC. Alpine's ~5 MB base image means this environment uses less RAM than one Windows VM while running 10+ isolated services.

Management

  • Portainer — Docker GUI

Running Docker inside an LXC gives two isolation layers. The LXC has its own filesystem and network namespace — no service affects the hypervisor host. Docker adds per-service isolation with defined resource limits. This mirrors how Kubernetes pods run on container-optimised nodes in cloud environments.

Business Continuity

Every design decision considers recoverability. Good backup habits here translate directly to managing production infrastructure.

Backup Strategy — 3-2-1 Rule

1
Hourly — Proxmox snapshots

Roll back any VM to any hour without touching others

2
Daily — Proxmox → TrueNAS ZFS replication

Full VM backups on a separate device — survives hypervisor failure

3
Weekly — Plex metadata snapshots

Rebuilding from scratch takes hours; from backup, under 5 minutes
